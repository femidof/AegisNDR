# MVP requirements matrix

Authoritative sources:

- `../Hybrid AI Network Defense Platform.pdf` (technical specification)
- `../Hybrid AI Network Defense Platform-1.pdf` (product requirements)

Statuses are evidence-based. `Implemented` means a directly relevant automated
test or runtime acceptance has passed; `Partial` means some required behavior is
implemented but the complete requirement is not yet proved.

| Requirement group | Status after Phase 1 | Current evidence or remaining proof |
|---|---|---|
| Single-node customer Compose | Implemented | Customer container acceptance starts and checks every required Phase 1 service. |
| Suricata and Zeek ingestion | Implemented | Deterministic replay produces both sources in ClickHouse; live AF_PACKET capture consumes the installer-selected interface through host networking (`SENSOR_CAPTURE_MODE=live`, `SENSOR_NETWORK_MODE=host`, `CAPTURE_INTERFACE`), which installer regression tests assert. A real mirrored interface still requires site deployment validation. |
| Continuous local detection | Implemented | Scheduled service persists an alert and evidence from sensor events; unit coverage proves operation with cloud and model disabled. The container-level offline-resilience gate (`scripts/test-offline-resilience.sh`, run in CI) stops the outbound connector and proves ingestion, detection checkpoints, alerts, investigations, cases, the local API, and the dashboard all continue while the control plane is unreachable. Offline sensor containers mark themselves healthy before PCAP replay and checkpoint completed replays, so restarts never re-ingest the capture and large captures cannot fail health gates. |
| Local PostgreSQL/ClickHouse/MinIO persistence | Implemented | Production-store integration and container acceptance cover schema/readiness and durable product flow. The metadata adapter applies versioned migrations (`local_state.schema_migrations`, versions 2-3 in code) so upgraded volumes converge without a container re-init; ClickHouse event search uses the indexed `search_text` token column. Event IP columns are String: missing addresses are stored as empty strings per the NormalizedEvent contract (never the unspecified `::`), and upgraded IPv6 columns are migrated in code. |
| Local API authorization and tenant isolation | Implemented | Strict JWT/JWKS, tenant/deployment assignment, role and machine/human boundary tests pass. The signing-key document is fetched only over verified HTTPS (pinned to the customer CA through the TLS ingress in production; the standalone local JWKS path is also HTTPS); plain-HTTP JWKS is rejected unless an explicit development-only override is set. RSA signing keys below exponent 65537 are rejected. |
| API transport hardening and concurrent write safety | Implemented | All product APIs run on a threaded production WSGI server with per-request timeouts, request-line/header/body caps, keep-alive, bounded concurrency, and verified mTLS peer fingerprints; outbound reads carry socket-level deadlines against stalled peers. Read-then-write operations (alert/case updates, investigation lifecycle, evidence-export approval, rule creation) execute atomically in single transactions or under the store lock with conflict guards, so duplicate alerts, lost updates, and TOCTOU approvals are impossible. Evidence-export approval documents are validated against the requested evidence set; demo-mode payload search uses an FTS5 index; rate limiters bound key size and total window entries. |
| Customer dashboard uses real APIs | Implemented | API contract/auth tests and production build pass; demo data is explicit configuration only. |
| Browser OIDC on a private LAN | Implemented | PKCE/OIDC client, private-LAN HTTPS ingress, same-origin API proxy and secure callback validation pass; a real headless-browser sign-in against the composed Logto deployment is exercised end-to-end (`scripts/test-browser-oidc.sh`), confirming dashboard and cloud-portal authentication, real API data, an authenticated alert mutation, and the metadata-only portal boundary. |
| Logto organizations, roles, permissions and apps | Implemented | Idempotent bootstrap creates both resources, seven organization roles, dashboard/cloud SPAs and deployment M2M identity; the ephemeral Management API seed is removed after reconciliation. |
| One-time enrollment and local P-256 identity | Implemented | Valid P-256 CSR, CA-signed client certificate, constraints, fingerprint, malformed/RSA rejection and one-time token behavior are tested. Fully air-gapped deployments use `--standalone` (local identity, local CA-signed certificate, local RS256 issuer with served JWKS and short-lived analyst tokens) with no control-plane connectivity; installer and API round-trip tests cover both paths. The deployment CA is provisioned by a dedicated init step before either control-plane service starts, and the connector mounts the installer-provisioned identity read-only with rotated certificates written to its own state volume. |
| Outbound-only connector lifecycle | Implemented | Heartbeat, aggregate usage, entitlement/policy/update refresh, retry persistence, idempotency and cert rotation tests pass; container has no published ports. |
| Provider-independent zero-retention gateway | Implemented | Standalone gateway, HTTP provider adapter (verified TLS, authentication, bounded SSE streaming), and fail-closed policy/schema boundaries exist; live acceptance tests exercise both buffered and streamed requests against a real TLS endpoint. A real contracted provider credential/endpoint remains a deployment input. |
| AI evidence minimization and local transmission ledger | Implemented | Redaction, unknown evidence/action rejection, offline failure and visible transmission tests pass. Drop-key matching is exact or separator-prefixed (no substring over-redaction), internal TLDs are configurable per deployment, emails with quoted local-parts/IDN domains and bearer tokens split by invisible Unicode format characters are all redacted; model request payloads reject unknown fields. |
| Cloud management portal | Implemented | Organization-token authorization, tenant isolation, one-time enrollment, fleet health/version/sensors, aggregate usage, entitlements, zero-retention policy, signed-update posture and support metadata are covered by API/UI/container tests; the proxy cannot reach customer analyst or machine endpoints. |
| Signed updates and customer-controlled rollback | Implemented | Unit coverage proves signed P-256 manifest verification, key pinning, digest-pinned staging, downgrade approval, post-apply health rollback, automatic rollback failure handling, and the append-only software-change audit chain. Image-level rollback reloads the digest-pinned offline archive of the previous release (persisted in install-state) without registry access. |
| Full analyst/admin views and workflows | Implemented | Core overview/traffic/alerts/investigations/cases/sensors/transmissions/audit/policy plus detection-rule tuning, suppressions, integrations (write-only credential rotation), and retention settings are API-backed; unit coverage proves scoped CRUD, role enforcement, and audit records for every admin flow. |
| Product audit coverage and immutability | Implemented | Every Local API audit action is exercised end-to-end (authentication, alert updates, case lifecycle, model policy, rule/suppression/integration CRUD, retention/settings, evidence-export request/approve/download, support bundles), each scoped to the signed deployment with a verifiable hash chain; immutability and role enforcement are tested. A global cross-scope hash chain detects whole-scope deletion, caller-supplied timestamps cannot backdate a scope chain, and metadata is restricted to JSON-primitive values so verification is byte-stable. |
| Private-network TLS and service encryption | Implemented | Host-locked HTTPS ingress exposes only 80/443 and proxies dashboard/API/Grafana; generated/supplied certificate validation and live TLS tests pass. The customer installer provisions a private internal CA by default and applies the internal-TLS Compose overlay, encrypting every credential-bearing hop (PostgreSQL, ClickHouse, MinIO, exporters, vector, Grafana) with verified TLS. The live `scripts/test-internal-tls.sh` acceptance proves plaintext Postgres connections are rejected (hostssl-only hba), the plaintext ClickHouse HTTP listener is disabled, MinIO TLS provisioning completes, and the full product flow runs over the encrypted hops. |
| Grafana/Prometheus/OpenTelemetry | Implemented | Grafana/Prometheus provisioning tests pass; a customer-local OpenTelemetry collector is composed, the local API and operations agent export bounded sanitized telemetry to it over OTLP, and Prometheus scrapes its product metrics endpoint. The operations-agent metrics endpoint and MinIO cluster metrics require scrape credentials (installer-generated token / MinIO JWT, parsed from `mc --json` output and stored owner-readable), Grafana supports optional Logto OIDC sign-in while the base Compose no longer publishes its port, and Prometheus waits for the exporters' health checks (the distroless OTel collector is covered by its health-extension probe). |
| Secure release supply chain | Implemented | Deterministic offline SBOM generation, code-only and image-bearing bundle verification (digest-authenticated images.tar, release image-pin override match, source and image SBOM digests, path-safety and safe extraction), release checksum/signature rejection, and update-agent manifest verification are all covered by automated tests. |
| Complete PDF end-to-end acceptance | Implemented | Capture-to-persisted-alert/evidence, authenticated API contracts, HTTPS ingress, portal paths, and a joined browser OIDC journey (dashboard + cloud portal, including an authenticated mutation and audit record) all pass; a real mirrored capture interface and contracted provider endpoint remain deployment inputs rather than product gaps. |

This matrix is updated after every phase review. Any `Missing`, `Partial`, or
unproved row feeds the next implementation plan.
